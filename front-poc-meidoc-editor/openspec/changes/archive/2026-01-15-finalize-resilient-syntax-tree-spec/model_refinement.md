# モデルの洗練と高度な機能

## 1. 座標系の最適化 (O(N) -> O(Depth))

### 問題点
すべてのノードに絶対的な `from` と `to` を保存すると、ドキュメントの先頭で 1 文字挿入するだけで、後続のすべてのノードの座標を更新する必要があります (O(N))。大規模なドキュメントでは、これは非効率的です。

### 解決策: 相対的な長さ
絶対座標 `from` と `to` を保存する代わりに、各ノードは自身の `length` のみを保持します。

- **保存されるプロパティ**: `length` (number)
- **計算されるプロパティ**: `from` (祖先と直前の兄弟をトラバースして計算)
- **計算されるプロパティ**: `to` (`from + length`)

`from` の計算を最適化するために、開始位置をキャッシュし、直前の兄弟または祖先が変更されたときにのみ無効化することができます。ただし、耐障害性の高いツリー（レンダリング中に頻繁に読み取られ、編集バッチ中に書き込まれる）の場合、単純なトラバースは遅くなる可能性があります (フルウォークで O(Depth) * ノード数)。

**実装の決定:**
**ハイブリッドアプローチ**を採用します:

1.  **真実の源 (Source of Truth)**: 各ノードの `length`。
2.  **キャッシュされた絶対座標**: `from` / `to` をキャッシュ（または動的計算）。
3.  **更新戦略**: ノードの長さが変更されたとき、その長さの変更を祖先にバブリング（伝播）させます。兄弟の `from` 値を直ちに更新することはありません。代わりに、V1 では `sampleContent.ts` がギガバイト単位ではないため、遅延計算または O(N) 更新を使用します。
4.  **洗練されたモデル**:

    ```typescript
    interface ResilientNode {
      parent: ResilientNode | null;
      children: ResilientNode[];
      length: number; // タグとコンテンツを含むこのノードの全長

      // キャッシュ (オプション/遅延)
      _cachedFrom?: number;
    }
    ```

    *補足*: 初期実装では、明確に文書化されている限り厳格な O(N) は許容されますが、アーキテクチャとしては「相対的な長さ」モデルの方が優れています。インターフェースは主に `length` に依存するように定義します。

## 2. ProseMirror リバースマッピング戦略

### コンセプト
ProseMirror (PM) のトランザクションを RST にマッピングし戻すのは複雑です。PM の操作はセマンティック (`ReplaceStep`, `AddMarkStep`) であるのに対し、RST の操作はテキスト/構造的であるためです。

### 戦略
1.  **ID マッチング**: RST のすべての `Defined` ノードに UUID を付与します。この UUID は属性/マークとして PM ノードに渡されます。
2.  **Step の解釈**:
    -   **テキストの更新**: ステップがマッピングされたノード内のテキストを変更した場合、ID で RST ノードを検索し、そのコンテンツにテキストの差分を適用します。
    -   **属性の更新**: RST の属性に直接マッピングされます。
    -   **構造変更 (分割/結合)**:
        -   *分割*: `<p>AB</p>` が `<p>A</p><p>B</p>` になった場合、PM は分割ステップを送信します。RST はノード構造を複製する必要があります。
        -   *汎用的なフォールバック*: 複雑なステップの場合、PM での影響範囲を特定し、その範囲を XML 文字列にシリアライズして、RST の対応する範囲を置換（スニペットを再パース）します。これにより、すべての PM ステップタイプに対して個別のロジックを実装することなく、正当性を確保できます。

**決定**: 構造変更には **「範囲シリアライズ・フォールバック」** を、テキスト/属性の変更には **「直接更新」** を実装します。

## 3. エラー回復: 自動クローズ戦略

### ロジック
パーサーは開始タグのスタックを使用します。閉じタグ `</X>` に遭遇したとき:

1.  `X` がスタックのトップにあるか確認します。
    -   はい: ポップして閉じます (標準)。
2.  `X` がスタック内にある（がトップではない）か確認します。
    -   はい: `X` より上のすべてのタグは「暗黙的に閉じられた」（または「未閉鎖エラー」）と見なされます。スタックを `X` までポップし、エラーノードを作成するか、厳格さに応じて単に閉じます。
    -   *洗練*: それらを `UnclosedNode`（エラーの一種）としてマークしつつ、ツリー内に保持します。
3.  `X` がスタックにないか確認します。
    -   結果: `</X>` は「孤立した閉じタグ」です。`Text` または `ErrorNode` (孤立) として扱います。

**決定**: 自動クローズのために **「一致するまでポップ」** 戦略を実装します。

## 更新されたコアモデル・インターフェース

```typescript
export type ResilientNodeType = "Defined" | "Text" | "Foreign" | "Error";

export interface ResilientNode {
  readonly id: string;
  readonly type: ResilientNodeType;
  parent: ResilientNode | null;
  children: ResilientNode[];

  // コアサイズ・プロパティ
  length: number;

  // コンテンツ
  tagName?: string;
  attributes?: Record<string, string>;
  textContent?: string;
  errorMessage?: string; // エラーノード用

  // ヘルパー
  get from(): number; // 計算（高コスト）またはキャッシュ
  get to(): number;   // 計算 (from + length)
}
```
